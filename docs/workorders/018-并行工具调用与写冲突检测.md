# 施工单 018：并行工具调用 + 写冲突检测

> 2026-09-04 起草并完成（用户授权连续推进）。三件事（AppContainer / 并行调用 /
> 组件总线）里**先做并行调用**：可测性最好（eval 体系直接复用）、不碰 Windows 安全
> 深水区。AppContainer → 019；组件总线 UI 插槽 → 019 一并拍板。

## 一、设计（窄而刚）

**现状**：agent.rs 核心循环对 `turn.tool_calls` **逐个串行**执行（判定→执行→回填）。
模型一次返回多个 tool_calls 时（常见：并行读多个文件再汇总），全部排队。

**新模型（判定与执行分离）**：
1. **判定阶段（串行，保持全部现有语义）**：逐个走 Plan 拦截（plan_block_reason）→
   审批（needs_approval_for / ask 弹窗）→ 记录 (approved, risk, plan_reason)。
   弹窗顺序 = 工具声明顺序，无交互并发问题。
2. **执行阶段（按档位分批）**：
   - **只读组**：approved 且 `risk == Safe`（只读工具/只读命令）→ **并行执行**
     （futures 并发，全部为无副作用操作，天然无竞态）；
   - **写/执行组**：approved 且 `risk >= Normal` → **串行独占**（保持现有 checkpoint
     + 沙箱语义，写类并行语义不可静态判定，不冒进）；
   - **写冲突检测**：同轮 `write_file` 出现相同 path ≥2 次 → 仅第一个执行，其余跳过并
     回喂「写冲突：本轮已有对同文件的写操作，已跳过，请拆分到下一轮」（JSONL
     `state kind:"write.conflict"`）。
3. **回填顺序不变**：tool 消息按 tool_calls 原顺序回填（协议友好）；tool_result SSE
   按实际完成顺序发（前端按 running 卡片匹配，已支持）。
4. **取消贯通**：判定前、并行批次后、串行每个工具前都检查取消标志。

## 二、明确不在本单

- shell/git 等执行型工具的并行（语义不可静态判定，保持串行独占）；
- AppContainer + 网络出向限制（019）；
- 组件总线 UI 插槽（019 一并拍板）。

## 三、验收底线

1. cargo test 基线只增不减（写冲突检测/分组逻辑补单测）；npm build 通过。
2. 真机冒烟：构造「并行读 3 个文件再汇总」任务，时间线面板可见只读工具并发完成
   （完成顺序与发起顺序无关），结果正确；写类任务行为与改造前一致。
3. 审批/Plan 拦截/取消语义与改造前一致（回归）。

## 四、红线

1. 审批判定单点不动（013 A2）；Plan 拦截优先级不变（016 B2）。
2. JSONL 6 类 schema 不动（新事件只作 state kind 扩展：write.conflict）。
3. 写类工具不并行（本轮红线；后续如有需求单独评审）。
4. 小步提交，中文 message，前缀 ` ...`。
