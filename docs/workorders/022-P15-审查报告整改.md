# 施工单 022 —— 审查报告整改（用户直派，2026-09-17）

## 起因

用户拿到一份外部模型对项目的审查报告（`agent-copy_审查报告_20260915.md.txt`，写于 P15 之前），
让我逐条核对「有没有值得优化的」，并说「你看着办」。

核对结论（详见对话记录）：报告的缺陷清单准确率较高（D1/D3/D4/D5/D6、S1 属实），
但**优先级排错**（把锁毒化放 P0），且有几条**误报**（「无可视化检查点回滚工具」——
cp-dock 的撤销按钮就是；「AGENTS.md 是空文件」——那是坑 13 写死的设计）。
本单只做「真问题 + 性价比高」的那批，`edit_file` 工具单开一轮（要动审批语义与工具表）。

## 交付

### A. 原子写（报告 D3）

- 新增 `src/fsx.rs`：`write_atomic`（同目录临时文件 → rename 替换）+ 3 个单测
  （替换不留尾、自动建父目录、失败不牵连旧文件）。同卷 rename 在 Windows 上走
  `MoveFileExW(REPLACE_EXISTING)`，不存在「写一半」的中间态。
- 接入 7 个落盘点：`write_file` 工具、`settings.json`、系统约定 `prompts/system.md`、
  双层 `AGENTS.md`（保存与模板）、`SKILL.md`、`HANDOFF.md`、首次生成的 `config.toml`。

### B. 降级链中途重流（报告 D4）

- 主渠道流到一半失败→换渠道重试时，前半截内容已经作为 `content` 事件推给前端了，
  界面会「半截 + 完整」叠着显示。
- 新增 `AgentEvent::StepReset { content, reasoning }`：换渠道前把**本次尝试已推送的
  UTF-16 码元数**（与 JS `String.length` 同口径）发给前端；SSE 记为 `{"reset":{...}}`；
  前端把当前消息尾部按这个数丢掉。核心聚合器本来就按 attempt 独立，不受影响。

### C. 服务层来源校验（报告 S1）

- 新增中间件 `guard_local_only`（最外层）+ 纯函数 `check_origin` / `split_host` /
  `is_loopback_host`（4 个单测）：
  1. `Host` 必须是回环（`localhost` / `127.x` / `[::1]`）——**DNS rebinding 就死在这一条**；
  2. 带 `Origin` 时必须是回环且**端口与 Host 一致**；`Origin: null`（沙箱 iframe / file://）拒；
  3. 无 `Origin` 的命令行客户端（curl / eval / 服务自管理）放行。
- `web/vite.config.js` 同步：代理转发时把 `Origin` 改写成主服务地址（否则热更模式会被 403），
  并把 `/ui-ext` 也纳入代理。
- 真机验证：伪造 Host → 403；跨源 Origin → 403；`Origin: null` → 403；本机另一端口 → 403；
  同源与无 Origin → 200。

### D. 顺手项

- `build_client()` 不再 `expect` panic（构建失败回落默认客户端 + 记 `gateway.client_fallback`）。
- **锁毒化自愈**：全仓 `.read()/.write()/.lock()` 的 `unwrap()/expect("…锁毒化")` 共 39 处
  统一换成 `unwrap_or_else(|e| e.into_inner())` —— 一次持锁 panic 不再让后续所有请求级联 500。
- `max_steps` 默认与 `config.toml` 由 8 → 16（读→改→跑测试→修→再跑就会撞顶）。
- 修掉一个**既有的脆弱测试**：`attachments_dir_appended_to_gitignore` 单独跑时会因 logger
  未初始化而 panic（`observability::event` → 改 `try_event`）。

### E. eval 多轮 + Plan 批准链路（报告 1.1 那条「未验证」）

- `EvalTask` 新增 `followup_prompt` / `followup_plan_mode`；`drive_chat` 拆出 `drive_turn`，
  第二轮把**完整历史**（含第一轮的 assistant 计划文本）一起发回——服务端以 `messages` 为消息源，
  只发一句「计划已批准」会丢上下文（第一版就这么翻的车：模型答「任务信息不足」）。
- 新任务 `plan-approve-execute`：第一轮 Plan 档出计划（不许动文件）→ 第二轮批准后执行 →
  断言 `plan_proposal` + 文件真的建出来 + `tool_call` + `done`。**真机 5/5 通过**（商汤渠道；
  tokeness/free 在同一任务上吐畸形输出 `<|tool_calls_section_begin|>`，属渠道问题非本项目）。

### F. 附带发现（文档与现实的偏差）

- **Plan/Act 界面入口其实是空的**：P9 交付过（b41d195），P14 的前端重写（c39e0d2）把它删了
  （代码里留了注释「改由模型按系统提示自动规划」——是有意移除），但 README 与 ROADMAP 仍在
  描述「输入框 Plan/Act 切换 + 计划卡 + 批准按钮」。已更正：README 两处改为「Plan 档 = 接口层
  能力（请求级 plan_mode），界面无手动入口」；ROADMAP P9 行补注移除时间与保留范围。
  后端能力（拦截 + plan_proposal）没删，eval 继续覆盖它。
- 服务层只校验 Host/Origin 的说明补进 README（运行形态节）。
