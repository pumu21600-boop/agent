# 施工单 006：P5 上下文工程 v1

## 项目背景（自行对齐）
- 依据 `docs/ROADMAP.md`（P5）：工具结果截断/压缩/分页、token 预算。
- 现状（P4 完成 tag v0.5-p4）：6 个工具、审批三档（Codex 式）、shell/git 沙箱可脱。
  当前上下文问题：工具结果只有 8000 字符硬截断；多轮对话历史无限膨胀，token 烧钱且可能撑爆窗口。

## 任务 A：token 估算（src/context/）
1. `estimate_tokens(text) -> u64`：无 tokenizer 依赖的启发式（CJK 字符 ≈1 token/字，
   ASCII ≈1 token/4 字符，取两者加权和）；`estimate_messages(&[Value]) -> u64` 汇总。
2. config `[context]` 节：`budget_tokens`（默认 96_000，低于主流模型窗口，给回复留余量）、
   `recent_tool_results_kept`（默认 6）。

## 任务 B：工具结果压缩（src/tools/ 或 context/）
1. 替换 chars 硬截断：**头尾保留**——头部 60% + 尾部 40%，中间插
   `\n……[中间省略 N 行 / M 字符，完整内容见日志]……\n`。
2. JSONL `tool_result` 事件加 `truncated: bool`（schema 增字段不增类型）。
3. 上限仍取 tool_result_max_chars（8000），shell/git/read_file/search/web_fetch 统一走它。

## 任务 C：历史裁剪（src/core/agent.rs 循环组装 messages 前）
1. 每轮请求前估算全 messages token；超 budget 才裁，不超不动。
2. 裁剪策略（从旧到新，保留最近 recent_tool_results_kept 个工具结果不裁）：
   - 超长的 tool 消息 → 替换为 `[工具结果已归档：{name}，原 {N} tokens]`
   - 仍超 → 更早的 assistant/tool 消息整体替换为占位
   - system 消息和最后一条 user 消息永不裁
3. 裁剪发生时落 JSONL：state `kind: context.compacted`（裁了几个、前后 token 估算）。

## 任务 D：分页查询工具（src/tools/）
1. `read_page`（danger 0）：`{path, page, page_size?}`——把大文件按页读（默认 200 行/页），
   返回带 `第 x/y 页` 头；供模型主动翻大文件，不再依赖一次读全。
2. 注册进工具表；描述里写明「大文件优先分页读」。

## 验收标准（全过才算完）
1. 工具结果超限 → 头尾保留 + 中间省略标记 + JSONL truncated=true
2. 构造超预算历史（mock 多轮工具结果）→ 裁剪触发、最近 N 个工具结果完好、system/末条 user 不动、
   JSONL 有 context.compacted
3. read_page 翻页正确（页码边界、不足一页）
4. budget_tokens/页大小可在 config.toml 调；默认值合理
5. cargo test 全绿（token 估算边界、压缩、裁剪、read_page 均有单测）
