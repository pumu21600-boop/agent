## 0. 一句话目标

agent 越用越懂用户，从不犯第二次同样的错；用户问"上个月做了什么项目"，能快速、毫不啰嗦地回答。

## 1. 已经建成的（代码已推送，正在跑）

### 1.1 记忆检索工具 `memory`（v0.32.31，commit d598657）

起因是用户实锤「让他检索记忆，他折腾半天」：模型为找记忆去翻应用源码、手解 3MB 的 library.json，52 秒 18 步没搜到东西。根因是语义记忆只有 UI 一条路——`/api/memory/search` 只有星云面板在调，agent 侧一个能调的工具都没有。

| 动作 | 作用 | 关键参数 |
|---|---|---|
| `search` | 语义 + 关键词混合检索，跨全部工作区 | `query`（必填）、`workspace`（可选，按项目过滤） |
| `recent` | 最近会话，按时间倒序 | `limit`（默认 10）、`workspace` |
| `similar` | 与某条会话相近的其它会话 | `id` |
| `read` | 读某条会话的对话原文 | `id` |

配套改动：
- **检索结果带身份字段**（标题/工作区/相对时间/消息数/命中片段/id）——原先 `Hit` 只有 id 和片段，agent 拿到也没法说「是哪条、什么时候」。
- **检索前先做有界增量同步**——索引原先只在开面板/定时到点时同步，中途聊的会话搜不到。指纹未变的条目不重算、不调嵌入渠道。
- **闸跟「记忆库」插件走**（`features.galaxy`）：关掉插件则界面入口与 agent 通道一起没，与浏览器插件同一套能力总闸语义。
- 系统提示加「以前的记忆」段，并写明**别翻 logs/ 目录、别解析 library.json、别读源码考古**。

### 1.2 会话转写提成共享函数 + 假提示修复（同 commit）

- 转写逻辑从 `/api/sessions/transcript` 提到 `session::transcript()`，面板端点与 memory 工具读原文同一条路，常量不各抄一份。
- 修 `omitted` 假提示：旧实现拿「保留数 < 总会话数」判定，带 tool 消息的会话明明没丢内容也报「只保留了最近部分」，前端 @引用 和 memory 工具都会因此对用户说假话。改为只认预算截断。

### 1.3 全局根搬家（v0.32.32，commit bec1d7c，**一半待回滚，见 §5**）

把记忆全局层从 `~/.agent` 搬到 `<app_root>/.agent`，启动时自动迁移（只复制、绝不覆盖、旧根永不删）。动机是同一台电脑跑几份 agent 时会共享一份 AGENTS.md。

## 2. 总体架构：三层记忆 + 双文件拆分

| 层 | 内容 | 载体 | 谁写 | 谁读 |
|---|---|---|---|---|
| **约定层** | 用户亲手写的全局约定 | `~/.agent/AGENTS.md`（按 Windows 用户，永久生效） | 用户手写 | 每轮自动注入 |
| **记忆层** | agent 自动总结的偏好与教训 | `<app_root>/.agent/profile.md`（按安装隔离） | agent 自动写 | 每轮自动注入 |
| **情节层** | 会话历史、事件流水 | `library.json` + `events.log` | 自动记录 | 按需检索（memory 工具） |
| **工作层** | 当前任务上下文 | 上下文窗口 | — | — |

**双文件拆分是本方案的核心**，两条铁律：

1. **`~/.agent/AGENTS.md` 是用户的地盘**，agent 绝不碰。全局约定的语义是「我这个人在所有项目里通用的设定」，本来就该按用户算，不随安装走。
2. **`profile.md` 是 agent 的地盘**，按安装隔离（换一份安装换一份记忆，互不干扰），只它写、只它读。

其他约定：
- `prompts/system.md` 是产品内置约定，**自动总结绝不动它**。
- 不做项目隔离：自动记忆进按安装隔离的 profile.md，跨项目共享。
- **注入顺序**（靠后优先级高）：`profile.md` → `~/.agent/AGENTS.md` → 项目 `AGENTS.md`。agent 推断的记忆优先级最低，用户手写的一律更高——冲突时听用户的。
- `index.json`（项目登记）继续按安装隔离，不动。

## 3. 自动记忆（写）

### 3.1 触发器（两类）

| 编号 | 触发条件 | 去处 |
|---|---|---|
| **T1 长期信号** | 用户消息含长期偏好信号（以后/一直/记住/每次/默认/长期……） | 偏好区 |
| **T2 重复踩坑** | 同一个坑出现第二次 | 教训区 |

**T1 的门槛是一次就够**——用户明说"以后都这样"是直接指令，不需要第二次佐证。

> **明确不做：「同一诉求被反复提」自动升级成偏好。**即使用户从没说"记住"，但三番五次提同一件事，也不自动记。原因：没有可靠的判定机制——去重搜索只回答"profile.md 里有没有相似条目"，不回答"用户提过几次"；而首次出现时既然没写进文件，第二次也搜不到，这条分支按任何写法都触发不了。更糟的是它和"临时性要求不记"冲突：用户这次提、下次还提的可能是个一次性需求。
> 真要这个能力，得先做"跨会话的用户消息语义计数"，那是独立功能，不在本方案内。当前只认**显式信号词**这一条可靠触发。

**不记清单：**
- 临时性要求（"用十个字内回答""这次先这样"）
- 一次性任务细节
- **项目专属事实**（某项目的技术栈、目录结构、项目约定）——这类进项目 `AGENTS.md`，不进全局 profile.md，否则在 A 项目养成的习惯会污染 B 项目

### 3.2 判定方式：模型当轮完成，不另起后台任务

总结**不另起后台任务、不另开模型席位**——由用户正在工作的模型在回答过程中直接完成：识别 → 提炼 → 写入，一气呵成。

- T1 的语义判断（长期信号 vs 临时要求）由模型按 system 约定直接做。
- T2 的"第几次"由**搜现有条目**判定，不数次数：
  1. 工具失败 → 模型先搜 profile.md 里相似的坑
  2. **搜到了** → 不是第一次踩，给那条记一次「又踩了」，满第二次转正式教训
  3. **没搜到** → 记一条「观察中」，先不当正式教训

  这样跨项目天然生效（profile.md 本来就不分项目），不需要新计数器、不需要全局账本，复用已有的 memory 检索。原「≥2 次才记」的语义一点没丢，只是换个实现。

### 3.3 `memory.write` 工具：行级操作，绝不整段重写

**这是本方案最关键的一条安全设计。**因为 profile.md 用户也能自由编辑（见 §6），如果 agent 整段重写偏好区/教训区，用户手改的内容会被覆盖。

工具收结构化指令，不是一整块新内容：

```
加一条 → { op: "add",    section: "prefs", text: "以后回答先给结论" }
换一条 → { op: "replace", section: "prefs", match: "原文…", text: "新文…" }
删一条 → { op: "remove",  section: "prefs", match: "原文…" }
```

- 读文件 → **只动这一行** → 原子写回。用户改的其他行一概不动。
- `replace`/`remove` 按原文匹配，**匹配不上就报错**（"这条不在了，可能你删了或改了"），不硬盖。
- **用户删掉的条目不会被偷偷加回来**——报错后由模型重新判断。
- 只写 `<app_root>/.agent/profile.md` 的偏好区/教训区；`~/.agent/AGENTS.md`（用户手写）绝不碰。

### 3.4 提炼、去重与冲突

- **一句话条目，≤40 字**，禁止原句照搬。这条写进 system.md 当隐性约束，同时在工具描述里再钉一遍。
- 写入前过现有 `sanitize`（sk-/Bearer/密钥字段打码）。
- 去重：新条目与现有条目语义重合则合并，不堆重复。
- 冲突：**新覆盖旧，直接改，不确认**（用户随时能在面板里删改，见 §6）。

### 3.5 条目结构：可审计，而不是一段散文

「什么该记」本质上只能靠语义判断（"这是长期偏好还是这次的要求"没有确定性规则可答），所以重点不是加更多规则，而是**让每条记录可追溯、可撤销**——污染从"看不见"变成"看得见、能删"。

每条条目带元数据，存在文件里的 HTML 注释中（人看不受影响，工具解析得到）：

```markdown
## 偏好区
- 以后回答先给结论，不啰嗦 <!-- src: 工作区 · 2026-10-09 · hits: 1 -->

## 教训区
- cargo test 失败先看前 50 行，别全量刷屏 <!-- src: agent-copy · 2026-10-08 · hits: 2 · 已确认 -->
- 某个偶发失败的观察条目 <!-- src: 工作区 · 2026-10-09 · hits: 1 · 观察中 -->
```

| 字段 | 含义 |
|---|---|
| `src` | **纯来源记录**（在哪个工作区第一次学到）。不表达适用范围——教训按设计就是全局的，A 项目学的坑在 B 项目同样有效 |
| 日期 | 第一次记的时间 |
| `hits` | **参考值，不是判据**。给人看的命中次数，模型数错不影响任何逻辑 |
| 状态 | `观察中`（未确认）/ `已确认`（被第二次佐证）；**仅教训区有条目状态** |

偏好区与教训区字段差异：**偏好区不带状态**（一次就够，无需佐证），但**带 `hits`**——用户再次用信号词提同一件事时，去重搜索会搜到它，走合并路径，`hits` +1（见 §3.6）。

### 3.6 元数据与清理的运行时语义

**`src` 不是污染标记，别拿它分组。**面板**按 `hits` 降序排**，不按 `src` 分组——按 src 分组会诱导用户删掉"在 A 学但其实全局有效"的教训。真正的污染信号是「`src` 是 A、之后在任何项目都没再命中过」，这种由 30 天清除自动收走，不需要用户判断。`src` 的用途只有一个：用户想问"这条哪来的"时答得上。

**读永不写。**`memory` 的 search/recent/similar/read 四个只读动作绝不改文件。

**`hits` 只在写路径上增长**，且只换那一行的元数据注释，正文一字不动。两条路径：
- **T2 失败路径**：工具失败 → 搜到相似坑 → `hits` +1
- **T1 去重路径**：用户再次用信号词提同一件事 → 搜到已有偏好 → 合并而非新增 → `hits` +1

两条路径的共同形态是"**写入前先搜，搜到就合并**"——`hits` 记录的正是"这条被再次提出的次数"。所以偏好区条目不会永远停在 1，也不会在面板里沉底。

**「第二次」的判据是"搜到"，不是数字。**教训从 `观察中` 转 `已确认` 的条件是"T2 检索搜到了已有条目"，`hits` 只是把这个事实写给人看。模型漏写/错写 `hits` 不改变任何行为。

**观察中清除：时间驱动，但不另起后台任务。**两个同步触发点，任一遍历到就清：
- **启动时**扫一遍 profile.md
- **每次 `memory.write` 时**顺带扫

清的是「`观察中` 且首次记录超过 30 天」的条目。静默执行，写 events.log 留痕。

**T1 与 T2 门槛不同，是故意的。**

| | 门槛 | 理由 |
|---|---|---|
| T1 偏好 | **一次就够** | 用户明说"以后都这样"，是直接指令，不需要第二次佐证 |
| T2 教训 | **要第二次** | 工具失败常常是偶发抽风，一次就永久留条会污染记忆库 |

对齐的动作：两者写入前都先搜一遍做去重，走同一个检索。

### 3.7 通知与审批

- **通知**：跟用户说一声，就一句话——"记住了：以后回答先给结论，已记入偏好区"。不展开、不啰嗦。
- **审批**：`memory.write` 定为**常规写操作**。只读档下每次记记忆都先问用户；自动档静默记；完全访问档照静默。只读档不许悄悄写，这是档位语义的底线。

## 5. 待回滚：全局约定路径搬回 `~/.agent`

> **这是当前线上的活 bug，不是排期项。** v0.32.32 已部署，正在跑的服务读的是 `<app_root>/.agent/AGENTS.md`，而用户习惯和文档指向的都是 `~/.agent/AGENTS.md`——此刻用户改后者，任何效果都没有。**必须在动工前先回滚，不能排进施工单排队。**

根因：我们不能指望每个用户都自己去删 home 目录里的旧文件，两份文件会永久并存，用户改哪份都不一定生效，是个死结。

**回滚不是改个路径就完事**：现在代码里 `global_dir()` 一个函数同时喂两个文件——
- `index_path()` = `global_dir()/index.json`
- `global_agents_path()` = `global_dir()/AGENTS.md`

而方案要求两者分离，所以要把全局根**拆成两个**：

| 文件 | 去处 | 理由 |
|---|---|---|
| `AGENTS.md`（全局约定） | `~/.agent/`（按 Windows 用户） | 「我这个人在所有项目里通用的设定」，按用户算，不随安装走 |
| `index.json`（项目登记） | `<app_root>/.agent/`（按安装） | agent 自己的账，语义上不冲突，保持 v0.32.32 的现状 |
| `profile.md`（自动记忆） | `<app_root>/.agent/`（按安装） | 见 §2 |

回滚做法：
- 拆出 `user_global_dir()`（`~/.agent`）与 `install_state_dir()`（`<app_root>/.agent`）两个根，各管各的文件。
- **冲突判定：以 `~/.agent/AGENTS.md` 为准。**用户一直以为在改的是那份，它是语义上的正主；v0.32.32 之后 `<app_root>` 那份可能被写过，**备份为 `AGENTS.md.bak` 不删**，用户想翻能翻。
- **两份都非空且内容不同时，启动时明确告知用户**（"发现两份全局约定内容不同，已以 ~/.agent 为准，另一份备份在 <路径>，请确认"）——不静默挑一份。
- 本机现状：两份都是 0 字节，无冲突，回滚零风险。
- 回滚后 `<app_root>/.agent/` 专供 profile.md 与 index.json，职责单一。

## 6. 管理与可控

### 6.1 设置 → 记忆面板：四个签并列

| 签 | 文件 | 可编辑 |
|---|---|---|
| 系统约定 | `prompts/system.md` | 是 |
| 全局约定 | `~/.agent/AGENTS.md` | 是 |
| 项目约定 | `<workspace>/AGENTS.md` | 是 |
| **自动记忆** | `<app_root>/.agent/profile.md` | **是** |

每个签都指明路径。自动记忆那一签顶部写明约定：

> 这个文件 agent 也会自动往里写。它只会**加新条目**、或**改它认得出的那一条**，绝不整段重写；你删掉的条目它不会偷偷加回来。你随时可以改。

**按 `hits` 降序展示**（读 §3.6 的运行时语义）：每条标出命中几次、什么时候学的。**不按 `src` 分组**——那会诱导用户删掉"在 A 学但全局有效"的教训。用户问"这条哪来的"时，`src` 答得上。

**沉底条目的去向，两个区不一样**（别混为一谈）：
- **教训区**：`观察中` 且 30 天没被二次命中的，自动清除（§3.6）。
- **偏好区**：**不会被自动清**。偏好"只记一次、之后再没重提"是正常情况（比如"我喜欢深色主题"），不代表它错了。沉底的死偏好靠**上限预警时的「压缩旧条目」**处理——那时把从未命中的偏好列给用户，逐条确认留不留。

### 6.2 上限与膨胀控制

同类实践（2026-10-09 实查，未经二次复核）：
- Claude Code 官方：CLAUDE.md ≤200 行
- 社区共识：理想 ~2.5k tokens（100–150 行），4k tokens 上限，5k+ 进入 context rot
- Codex：AGENTS.md 硬截断 32 KiB

**注意：那些"100–150 行"的口径是英文短句，我们的条目带元数据，不能直接套行数。**

单条开销实算（**全文统一按 1.0–1.3 token/字符估算**——中文在主流 tokenizer 下约 1–1.5 token/字，取保守区间）：

| 组成 | 字符 | token 估算 |
|---|---|---|
| 正文（≤40 中文字） | ~40 | ~40–52 |
| 元数据注释 `<!-- src: X · 2026-10-09 · hits: 2 · 已确认 -->` | ~35 | ~35–46 |
| Markdown 符号与换行 | ~3 | ~3 |
| **合计** | **~78** | **~78–101** |

**结论：只用字符一把尺子，不并行用行数。**理由——每条长度已被"≤40 字"约束住，行数不再是独立变量；双口径必然出现"哪个先到"的死阈值问题（40 行 ≈ 3120 字符，早已越过任何合理的字符硬顶，行数口径永远够不着）。

| 项 | 值 |
|---|---|
| **硬顶** | **2500 字符**（按 1.0–1.3 token/字符 ≈ 2.5k–3.3k token，对应社区共识的 4k 上限） |
| **预警线** | **2000 字符（80%）**，此时约 25–26 条 |
| **理想区间** | 1200 字符以内（约 15 条），对应"理想 2.5k token" |
| 用户手写的 `~/.agent/AGENTS.md` | **不计入、不限制**——那是用户自己的地盘 |

预警时给用户三个选项：压缩旧条目 / 归档到文件 / 提高上限，由用户选。走现有通知通道。

日常防爆：总结时强制一句话提炼 + 语义去重，治未病。

## 7. 隐私

- 总结前走现有 `sanitize`（sk-/Bearer/密钥字段打码）。
- **含敏感信息的候选直接丢弃不记**——需要新增一步检测：现有 `sanitize` 只会打码、不会判定"该丢"，得先判断再决定记不记。
- 只记偏好和教训，**不记具体账号、密码、地址等实体值**。
