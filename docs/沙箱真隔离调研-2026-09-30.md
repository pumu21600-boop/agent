# 沙箱「真隔离档」调研（2026-09-30）

> 缘起：用户指出当前「沙箱」只是削权（受限 token + 工作区围栏），不是隔离运行环境——「没有给它一个隔离运行的环境就叫不上沙箱」。本报告调研三条真隔离路线的可行性、接入形态与代价，供拍板。

## 一、机器现状（实测）

- Windows Pro（EditionID=Professional），固件虚拟化已启用、SLAT/DEP 全过——**Windows Sandbox 与 WSL2/Docker 的硬件门槛全部满足**；内存 32G。
- Windows Sandbox 功能件**未启用**（System32 无 WindowsSandbox.exe；启用需管理员跑 `Enable-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM -All` + **重启一次**）。
- WSL：框架在、无发行版；Docker：未安装。

## 二、三条路线对比

| | **Docker Desktop（推荐）** | **Windows Sandbox** | **WSL2 直用** |
|---|---|---|---|
| 隔离强度 | 真·独立环境：独立文件系统/网络栈，容器毁掉即走 | 真·一次性虚拟机，关机即焚，每次全新 | 真·VM，但里面是 Linux |
| 程序化控制 | **`docker exec` 干净利落**，长驻容器、秒级进 | 只有「生成 .wsb（工作区映射+LogonCommand）→ 启动」一种发令方式，**启动后无法追加命令**（22H2 新 CLI 也只是 wsb execute 的启动形态）；要持续对话得在沙箱里驻一个监听程序轮询映射目录——hack | `wsl.exe` 进得去，但命令全是 Linux 语义 |
| 工作区交换 | bind mount 双向实时，路径做一次前缀映射 | MappedFolder 映射（可写），每次启动重新映射 | /mnt 或 \\wsl$，可配 |
| 工具链 | 做一个预装 git/node/python 的镜像，随时可用 | 每次全新系统，工具链要么 LogonCommand 现装（每轮数分钟）要么放弃 | 装一次常驻，但全是 Linux 工具 |
| 频率适配 | **适配现在「高频小命令」的工具循环** | 只适合「整段任务一次性丢进去跑完」 | 适配频率但不适配语义 |
| 代价 | 装 Docker Desktop（个人/小团队免费[1]）+ WSL2 后端；常驻约 1-2G 内存 | 启用功能件要重启一次；免装第三方 | 轻装，但语义偏移最大 |

**结论**：**Docker Desktop 路线**最贴合产品形态——agent 的 shell/git 工具循环是高频小命令，需要「长驻 + 随时 exec」，只有容器给得了。Windows Sandbox 的控制模型决定了它只适合将来做「整任务隔离跑」的补充档，不适合接进现有工具循环。WSL2 会让 agent 从 Windows 世界搬进 Linux 世界，偏移最大，不推荐。

## 三、接入形态（拍板 Docker 后的施工轮廓）

1. 配置：`[sandbox] mode = "isolated"`（新档），`isolated_runtime = "docker"`；与 restricted/appcontainer/unsandboxed 并列，审批档位语义不变。
2. 命令面：shell/git 工具从「本机 CreateProcess」改路由 `docker exec <容器> <命令>`；工作区 bind mount 进容器固定路径，宿主↔容器路径前缀映射（工具层已有 workspace_root 单点，改造面集中）。
3. 文件面：read_file/write_file/edit_file 仍在宿主直写（容器与宿主看见同一份挂盘），不搬进容器。
4. 镜像：做一个预装 git/node/python 的基础镜像（首次构建或拉取一次，之后秒起）。
5. 保险丝：容器层超时/资源上限 + 沿用 Job 思路（docker stop 兜底）；自检探针出 docker exec 版（echo/越界写/断网验证/超时击杀）。
6. 明说边界：容器内是 Linux，cmd 专用脚本/PowerShell 不可用；Windows 特有工具（注册表等）天然不进容器——这本来就是隔离的一部分。

工作量估计：接线 1 个施工单（配置+路由+路径映射），探针与自检 1 个；用户侧一次性动作 = 装 Docker Desktop（管理员，WSL2 内核）。
